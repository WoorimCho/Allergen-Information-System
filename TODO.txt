------------------------------------------------------------------
MIGRATION STRATEGY
------------------------------------------------------------------
Build each service to a feature-complete v1 ALONGSIDE the still-intact
monolith. Do not gut the monolith incrementally - it keeps owning its
tables and serving its UI as the fallback. When every catalogue is proven,
do the cutover in one pass (Phase 3).

------------------------------------------------------------------
DECISIONS LOCKED
------------------------------------------------------------------
- Monolith -> BFF only. Phase 3 retired its Thymeleaf CRUD; it is now a
  stateless BFF + auth gateway (no DB). SUPERSEDED the old "monolith evolves
  into UI + BFF" plan: the UI is now its OWN service (Projects/UI, :8081,
  Spring Boot 4.1.1 + Thymeleaf), a thin server-rendered client that calls the
  catalogues + User directly and the BFF for the composed view + calculators.
  It logs the user into the BFF and relays that JSESSIONID.
- Food + Ingredient = ONE entity, fully unified, in IngredientCatalogue. No
  separate Food entity and no /api/foods. Any sub-distinction (e.g. "raw /
  edible without cooking" vs "processed") is a tag such as form:raw, not a
  field. Whether a recipe produces or uses an entry is a RecipeCatalogue concern.
- Recipe references catalogue entries by id only (cross-service, no FK).
- User is ITS OWN service (Projects/User, :8084), not a BFF module.
- DB topology: ONE MySQL instance, one schema per service (mydatabase,
  ingredient_catalogue, recipe_catalogue, user_service). Created by
  Projects/infra/mysql-init on first boot.
- Auth: BFF-ENFORCED SESSION. POST /bff/login checks credentials against the
  User service and issues a session cookie; /bff/** requires it. Services stay
  identity-agnostic (trusted network) - the BFF is the enforcement point.
  Swap point if it ever moves to OAuth2: bff/BffSecurityConfig.

DECISIONS STILL OPEN
- (resolved 2026-09-08) Spring Boot version: all four services on 4.1.1.

PHASE 1 - BUILD THE SERVICES                            [COMPLETE]
==================================================================
All four services (IngredientCatalogue, RecipeCatalogue, User, GoodNight) are
v1-done, tested and Docker-verified. The BFF composes them, personalises for
the logged-in account, and enforces a session. Remaining [ ] items below are
Phase 2, the Phase 3 cutover, or "Later" polish - flagged inline.

Per-slice extraction recipe (repeat for each domain):
  1. Start from the catalogue template (copy the IngredientCatalogue skeleton)
  2. Copy the entity; cut every cross-aggregate @ManyToOne/@ManyToMany,
     replace with Long / Set<Long> id fields
  3. CrudRepository -> JpaRepository (+ JpaSpecificationExecutor)
  4. @RestController + DTO records (return JSON, not view names)
  5. Own schema + Flyway V1__init.sql
  6. Move that domain's logic out of the monolith's BasicServiceImpl into the
     service's own @Transactional service class
  7. Parity: tests, Dockerfile, compose "app" service, actuator, openapi.yaml
  Keep the monolith working against its own DB the whole time; flip the UI to
  call a service only after that catalogue is proven.
